# Builder → Salesforce procedure records

The builder remains the web application at `/` with its review page at `/salesforce`. Salesforce receives the approved schema and procedure data; it does not host the builder's Python runtime.

After scanning a repository, approve the Procedure entity and desired fields. Choose exactly one source procedure ID as a **unique external ID for record updates**. New catalog candidates propose that flag visibly; existing saved reviews can enable it using the checkbox beside the identity field. Saving alone never changes Salesforce. Validation/deployment includes the unique external-ID constraint, so existing duplicate values may block deployment and must be reviewed separately.

Save the review and inspect **Approved procedure records**. The preview identifies the target object, record count, match key and exact fields (including Salesforce's required Name, populated from the approved ID). Select **After successful schema deployment, sync the procedure records using only the approved fields**, then validate and deploy as usual. Check-only validation does not write records. Record sync starts only after metadata deployment succeeds and rechecks the saved review and record preview digests.

The data comes from the server-saved procedure catalogs discovered from the uploaded source, not browser-supplied record payloads. DIPs, MOPs, SOPs and runbooks share the reviewed Procedure mapping. Original source ID aliases map to the chosen identity target. Duplicate IDs across catalogs block sync; they are never arbitrarily merged. Missing properties are omitted and grouped by column set for bulk upsert, so absence does not clear existing values. Only approved fields are synced. Structured step data requires LongTextArea. There is no deletion, baseline update or permission to execute remediation.

Sync reuses the existing Salesforce Bulk API upsert helper. A live object/field/length/permission preflight runs before data writes, and confirmed completion with zero failures is required. Bulk operations are not transactional; a failed record sync can follow a successful schema deployment or partially imported data. The result retains the schema outcome and bulk job information. Resolve the failure and rerun the reviewed deployment/sync; unique external IDs match existing records rather than creating repeated copies.

The target remains **hackfest-developer**, with the existing local same-origin/CLI authentication boundary. This implements the workstation flow today. AWS hosting still needs authenticated Salesforce service credentials and a suitable server authorization boundary; exposing the local-only CLI endpoints publicly is not part of this change. No live Salesforce or AWS changes were performed during development.

Existing metadata object naming remains repository-hash scoped. This feature updates records within the approved target object; it does not reconcile different object namespaces generated by changed ZIP bytes or automatically migrate older MIM_DIP__c records into the current object. The separate MIM reader must be configured to the same object/field mapping before claiming end-to-end decision integration.

The sync checkbox now explains its prerequisites beside the control. Use **Show required procedure ID** to locate the source identity without changing any decisions. The separate **Show fields** filter offers Approved, Needs review and Rejected views; approval dropdowns continue to change decisions rather than filtering records. Filtering never changes saved approvals or validation state.
